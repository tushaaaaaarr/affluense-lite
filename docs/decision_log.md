# Decision log

| # | Options considered | What I chose and why | What would make me change it |
|---|---|---|---|
| 1 | LangGraph/CrewAI vs plain Python | Plain Python. The flow is a straight line with a few ifs; I can explain every line. | Need retries with saved state, human approval pauses, or parallel per-person branches. |
| 2 | One agent per event vs one per person vs split by skill | Split by skill: extract (LLM), brief (LLM), the rest is code. A per-person agent would repeat the same document-reading cost for each person. | If each person needed deep separate research (profiles), per-person agents would make sense. |
| 3 | Trust the model's citations vs verify them | Verify in code: the model must give a word-for-word quote; if it's not in the source, or a number isn't inside the quote, it's dropped. Cheap and catches the worst failure (invented numbers). | If tables extracted from PDFs break quotes too often, switch to table-aware parsing. |
| 4 | Auto-merge similar names vs stay careful | Careful: merge only on very close matches; "R K Sharma" vs "Rajesh Kumar Sharma" stays separate with lower confidence. A wrong merge is worse than a duplicate. | If RMs say they see too many duplicates, add a 2nd signal (company, role) to merge safely. |
| 5 | One number vs a range for amount | Range with working, and an "up to" factor of 0.5 labelled as my assumption. Filings say "up to". | Once basis-of-allotment data is available, use the actual shares sold. |
| 6 | Let an LLM browse for follow-ons vs LLM returns URLs only | URLs only, then same fetch->verify path; plus a free ledger of past runs. Hard stops: depth 1, top 3 people, 2 URLs, $ cap. | If results are mostly noise, drop web follow-on and use only the ledger. |
| 7 | Strong model vs cheap model | Cheap model by default because extraction is guarded by verification. | If the drop rate of verified quotes is high, test the stronger model on extraction only. |
| 8 | Include organisations in the ranked list or separate | Separate "institutional sellers" list: an RM can't call "Tiger Global". | If the client has an institutional desk, give them their own list. |
| 9 | Event choice | (1) **IPO:** SEDEMAC, Mar 2026. 100% existing shareholders selling, with named sellers and share counts in the RHP. (2) **Buyback:** Astrotalk ESOP buyback, Aug 2026. A private company with news-only evidence and mostly unnamed employees. (3) **Third, a different kind:** Restaurant Brands Asia (Burger King India) acquired by Inspira Global, 20 Jan 2026 (NSE press release). Only **one** party gets cash: QSR Asia Pte. Ltd. (Everstone) sells its 11.26% for ~₹460 crore, and it's a company. The ~₹1,500 crore in new shares and warrants goes to RBA itself. The people named are the **buyer** (Aayush Madhusudan Agrawal, who also appears as "Aayush Agrawal"), his co-promoter Madhusudan Agrawal, RBA's CEO, an Everstone co-founder and a Burger King executive. None of them is stated to have received money. So this tests what the other two don't: **direction of money** (don't list the buyer), **not inferring wealth** (an Everstone co-founder isn't personally paid in the filing), and **name traps** ("Madhusudan" is the son's middle name and the father's first name). The right output is no individuals to call, with QSR Asia in the companies list. I found the event through Screener but cite only the NSE filing. **Extra run, not one of the three:** Jio Platforms IPO, Oct 2026. It's 100% new shares, and "selling shareholder" appears 0 times in 591 pages, so it checks that the system says "no one to call" instead of inventing sellers. I first thought Jio could be the third event, but it's still an IPO. | If reviewers count "OFS IPO" and "fresh-issue IPO" as different kinds, Jio could be the third. |
| 10 | Model returns numbers (`amount_inr: 1200000000`) vs model copies the words (`"Rs 120 crore"`) and code converts | Copy the words. My first version asked for integers, and then every news amount failed my own check, because "1200000000" never appears in a sentence that says "120 crore". So the check was right and the design was wrong. Now the model never does arithmetic; code parses crore/lakh/million and USD (USD uses a fixed rate shown in the working). | If a source writes amounts in a form my parser doesn't know (e.g. "Rs 1.2k cr"), add it to the parser, not the prompt. |
| 11 | Mix follow-on quotes into a person's evidence vs keep them apart | Apart. A quote about a 2024 deal is true but it's not evidence for *this* event, and mixing them also inflated the "2 separate sources" confidence boost. Follow-on costs are now charged to the parent event so they count against the $2 cap. | If RMs want a full "money history" per person, that becomes its own section/profile. |
| 12 | Trust the model's "role" vs require it in the quote | Require it. "Name and role as the source names them" means the role is a fact like any other; if the quote doesn't say "Promoter", we show "role not stated in quote". Costs some roles that sit in a table header. | If too many roles go missing on RHP tables, pass the table header along with the row. |
| 13 | Lock to one LLM provider vs a small switch | Small switch (`AFF_PROVIDER` = anthropic or openai), about 15 lines in `engine/shared/llm.py`. I didn't know which provider Klypup's key would be for, and a live demo that can't start is the worst outcome. Web follow-on stays Anthropic-only; the free ledger works with both. | If one provider is confirmed, delete the other branch. |
| 14 | Respect robots.txt via Python's `RobotFileParser.read()` vs fetch robots.txt myself | Fetch it myself with my own User-Agent. The built-in reader got a 403 from tradejini and then treated the *whole site* as forbidden, even though their robots.txt only blocks `/admin/`. Still obey it; just read it properly. | If a site has no robots.txt but its terms forbid scraping, add it to `BLOCKED_DOMAINS` by hand. |
| 15 | One model call per person's call note vs one call for a batch of people | Batch of 10. The first real SEDEMAC run made 14 calls, took 8 minutes, and the rerun hit Gemini's free-tier limit (20 requests/day) on the 3rd note. Batched: 4 calls for the whole IPO, 20 s, $0.02. The number check still runs on each note separately against *that* person's facts. | If one person's note keeps failing, or notes start borrowing facts from the person next to them, go back to one call each for the top few. |
| 16 | Gemini 3.5 Flash ("thinking" model) vs 3.5 Flash-Lite | Flash-Lite. Flash hid its thinking tokens from the `completion_tokens` count (6 in, 1 out, 79 total on a test call) while Google bills them as output, so my cost log under-counted. I now count `total - prompt`. Flash also used up its token limit on thinking and cut a call note off mid-sentence. Flash-Lite has no hidden thinking, costs $0.30/$2.50 vs $1.50/$9.00 per 1M, and verification catches its mistakes the same way (decision 7). Newer 3.7/3.8 Flash kept returning 503 "high demand". | If extraction misses sellers that Flash finds, use Flash for extraction only. |
| 17 | Treat ESOP holders as sellers ("proceeds") vs label it as shares held | Label it. On a re-run the model also picked up 8 employees from the RHP's ESOP allotment history (page 111). The brief lists "holds ESOPs" as a valid reason, so they stay, but their range says "value of ESOP shares held, at the offer price; not cash unless they sell", and timing is "unknown" (vesting rules). | If the client only wants people with cash in hand, filter `esop` out of the call list. |
| 18 | Pick the model by name in code vs in `.env` | In `.env` (gitignored), with `.env.example` committed. On the day I ran it, `gemini-2.5-flash` was retired for new keys, and 3.7/3.8 were overloaded. The model had to change twice in an hour without touching code. Prices for each model sit in `config.py` with the date I read them. | If one model becomes the long-term standard, pin it in config and drop the env override. |
